# Backend Permission System Implementation Guide

## Overview

This guide provides step-by-step implementation to enhance your existing backend with the proper permission system that matches the frontend requirements. It focuses on implementing scope-based data filtering and permission-driven API responses.

---

## Step 1: Update Database Schema for Permissions

**Goal:** Ensure your database schema supports the granular permission system.

**Implementation Details:**
- Verify role_permissions table has all required boolean fields
- Add indexes for performance on permission queries
- Ensure proper foreign key constraints

**Expected Schema:**
```sql
-- role_permissions table should have:
CREATE TABLE role_permissions (
  id INT PRIMARY KEY AUTO_INCREMENT,
  role_id INT NOT NULL,
  module_id INT NOT NULL,
  submodule_id INT NULL,
  can_create BOOLEAN DEFAULT FALSE,
  can_read BOOLEAN DEFAULT FALSE,
  can_update BOOLEAN DEFAULT FALSE,
  can_delete BOOLEAN DEFAULT FALSE,
  can_view_all BOOLEAN DEFAULT FALSE, -- Key field for scope
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  
  FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE CASCADE,
  FOREIGN KEY (module_id) REFERENCES modules(id) ON DELETE CASCADE,
  FOREIGN KEY (submodule_id) REFERENCES submodules(id) ON DELETE CASCADE,
  
  -- Indexes for performance
  INDEX idx_role_module (role_id, module_id),
  INDEX idx_module_permissions (module_id, can_read, can_view_all),
  UNIQUE KEY unique_role_module_submodule (role_id, module_id, submodule_id)
);
```

**Cursor Prompt:**
```
Review and update the database schema to ensure proper permission system:

1. Verify role_permissions table has all required fields: can_create, can_read, can_update, can_delete, can_view_all (all BOOLEAN)
2. Add proper indexes on role_id, module_id, and permission fields for performance
3. Ensure foreign key constraints are properly set up
4. Add migration script if changes are needed
5. Update Prisma schema if using Prisma to reflect these changes
6. Verify users table has is_superadmin BOOLEAN field
7. Ensure tenant_id is properly indexed in all relevant tables
8. Add any missing indexes on frequently queried fields (user_id, tenant_id, created_at)
```

## Step 3: Enhance Authentication Middleware

**Goal:** Update auth middleware to attach resolved permissions to request object.

**Implementation Details:**
- Extend authMiddleware to include permission resolution
- Attach user permissions to req.user object
- Handle permission caching for performance
- Support for permission refresh on role changes

**Enhanced Request Object:**
```typescript
interface AuthenticatedRequest extends Request {
  user: {
    id: string;
    email: string;
    tenant_id?: string;
    is_superadmin: boolean;
    is_active: boolean;
    permissions: {
      [moduleKey: string]: {
        canCreate: boolean;
        canRead: boolean;
        canUpdate: boolean;
        canDelete: boolean;
        canViewAll: boolean;
      }
    };
    dataScopes: {
      [moduleKey: string]: {
        scope: 'all' | 'tenant' | 'own';
        tenantId?: string;
        userId?: string;
      }
    };
  };
}
```

**Cursor Prompt:**
```
Enhance the existing authMiddleware in src/middleware/authMiddleware.ts:

1. After JWT verification and user loading, resolve user permissions using PermissionService
2. Attach permissions object to req.user with module-based permission mapping
3. Pre-calculate dataScopes for common modules and attach to req.user
4. Implement permission caching with 15-minute TTL to avoid repeated DB queries
5. Add permission refresh mechanism when user roles change
6. Handle superadmin users by bypassing permission resolution
7. Add proper error handling for permission resolution failures
8. Create TypeScript interface for enhanced req.user object
9. Add logging for permission resolution debugging
10. Optimize queries to fetch user, roles, and permissions in minimal DB calls
```
